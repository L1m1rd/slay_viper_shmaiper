# Переход SLAY AWARD на Firebase

## Текущий этап

Создан проект `slay-award-2026` (SLAY AWARD 2026), тариф Spark.
Зарегистрировано веб-приложение SLAY AWARD Website, публичная конфигурация
записана в `backend-config.js`. Включён вход Email/Password.
Создана база Firestore Standard `(default)` в регионе `europe-west3` (Frankfurt).

Правила из `firestore.rules` опубликованы через Firebase Console.
Получен предварительный локальный экспорт Supabase: 2 аккаунта, 2 профиля,
3 строки голосов (1 документ голосования). Экспорт хранится вне папки сайта
и репозитория. Проверка плана переноса прошла; поддержаны старые имена
пользователей длиной до 64 символов, новая регистрация ограничена 30.
Пользователь разрешил административный импорт. Создание ключа запрошено
в консоли, но файл ключа не получен: скачивание не подтвердилось.
Каталог, аккаунты и голоса ещё не импортированы. Записи в Supabase
пока доступны; перед окончательным импортом нужно остановить записи
и повторить экспорт. Переключатель сайта остаётся на Supabase
до завершения миграции и проверки входа.

Подготовлен переход с Supabase на Firebase Authentication и Cloud Firestore
Standard edition. Текущий сайт использует Supabase, пока в `backend-config.js`
не выбран Firebase. VPS и Cloud Functions для этой реализации не нужны.

## 1. Создать проект

1. В https://console.firebase.google.com/ создать проект в своём аккаунте.
   Использовать бесплатный Spark, не включать платный Blaze для этой задачи.
2. Добавить Web app и скопировать публичные `apiKey`, `authDomain`, `projectId`,
   `appId` в `backend-config.js`. Пока оставить `provider: 'supabase'`.
3. Authentication → Sign-in method → включить Email/Password.
   В Settings → Authorized domains добавить домен текущего сайта и домен
   отдельного предпросмотра. Проверить шаблоны писем подтверждения email.
4. Firestore Database → Create database → Standard edition, Native mode,
   выбрать регион в Европе. Начать с Production mode. Регион потом не меняется.
5. Project settings → Service accounts → создать приватный JSON-ключ для
   одноразового переноса. Хранить **за пределами публичной папки сайта**.
   Этот файл нельзя отправлять в чат, коммитить или публиковать.

## 2. Подготовить каталог и правила

Из папки `site` (Node.js 22+, для эмулятора Java 21+):

```powershell
npm.cmd ci
npm.cmd run catalog
npm.cmd run test:migration
npm.cmd run test:backend
npm.cmd run test:rules
npx.cmd firebase login
npx.cmd firebase deploy --only firestore:rules,firestore:indexes --project YOUR_PROJECT_ID
```

`firebase-catalog.json` генерируется из существующих номинаций сайта.
При изменении участников необходимо пересобрать и обновить каталог в Firestore
через доверенную административную среду: браузер не может менять его.
Регистрации сначала получают `user/pending`, администратор одобряет их отдельно.
Голосовать могут только одобренные пользователи с подтверждённым email.
Роли, статусы и чужие голоса защищены правилами Firestore.

## 3. Экспортировать данные

Перед финальным экспортом временно запретить записи **на стороне Supabase**:
регистрацию, изменение профилей, голосов и статусов. Одной надписи на сайте
недостаточно — старые открытые вкладки могут продолжать отправлять запросы.
Записать точное время начала переноса, сделать резервную копию проекта.

В Supabase SQL Editor выполнить `scripts/supabase-export.sql`.
Сохранить единственное JSON-значение результата в файл
`migration-private/supabase-export.json` (без внешней обёртки результатов SQL).
Файл содержит email, bcrypt-хеши паролей и голоса. Он исключён из Git,
но **не должен находиться в публикуемом каталоге статического хостинга**.
Для реального переноса лучше хранить его вне репозитория и передать `--input`.

Предварительная проверка, без сети и записи:

```powershell
node scripts/migrate.mjs --input C:\Private\supabase-export.json
```

Скрипт проверяет совпадение пользователей и профилей, логины, роли, статусы,
участников, уникальность мест и максимум три выбора. Некорректные данные
останавливают импорт. Пользователи без bcrypt-пароля требуют отдельного решения,
скрипт не сбрасывает им пароль автоматически.

## 4. Перенести в новый проект

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS = 'C:\Private\firebase-service-account.json'
node scripts/migrate.mjs --input C:\Private\supabase-export.json --apply --project YOUR_PROJECT_ID
Remove-Item Env:\GOOGLE_APPLICATION_CREDENTIALS
```

Сохраняются UID, email, bcrypt-пароли, подтверждение email, профиль, роль,
статус и голоса. История сессий не переносится: пользователи входят заново.
Администратор сохраняется из старой базы. Его статус должен быть `approved`,
email подтверждён. Создание администратора из браузера запрещено.

Скрипт создаёт каталог, профили, резервирует логины и группирует голоса в один
документ на пользователя и номинацию. Три места сохраняются вместе — ошибки
между удалением и вставкой больше не теряют голоса.
Существующие отличающиеся документы и посторонние аккаунты вызывают остановку;
скрипт не перезаписывает их. После частичного сбоя можно повторить импорт с тем
же неизменным экспортом, пока целевой проект закрыт для пользователей.
Не запускайте повторный импорт после открытия голосования.

## 5. Проверить и переключить

Сначала запустить отдельный предпросмотр с `provider: 'firebase'` и проверить:

- вход обычного пользователя старым паролем и вход администратора;
- совпадение количества профилей и голосов с выводом dry run;
- сохранение обычных трёх мест и голосования за пару;
- невозможность голосования для pending/banned/admin;
- регистрацию нового пользователя, подтверждение email, одобрение и бан;
- редактирование имени, выход, повторный вход и итоговые результаты.

Только после этого изменить `provider` в основном `backend-config.js` на
`'firebase'`, опубликовать сайт и открыть записи в Firebase. Supabase оставить
замороженным как резерв на время перехода. Откат переключателя безопасен только
до новых записей в Firebase; после них нужен обратный перенос данных.
По завершении удалить/отозвать одноразовый ключ service account и убрать
приватные экспортные файлы из папки сайта.

## Лимиты

Spark не требует собственного сервера, но квоты сохраняются: Firestore включает
1 GiB, 50 000 чтений и 20 000 записей в сутки. При превышении бесплатных квот
операции могут перестать работать. Письма Authentication имеют отдельные квоты.
В опубликованных условиях нет недельной паузы проекта за неактивность.
Доступность из сетей участников нужно проверить перед переключением.

- https://firebase.google.com/docs/firestore/quotas
- https://firebase.google.com/pricing
- https://firebase.google.com/docs/auth/admin/import-users
- https://firebase.google.com/docs/firestore/security/rules-conditions

## Что проверяется локально

`test:migration` проверяет сохранение мест, ролей и статусов, обработку коллизий
и некорректных данных. `test:backend` проверяет выбор провайдера и сохранение
голосов при сбое записи. `test:rules` запускает настоящий эмулятор Firestore и
проверяет доступ к голосам, повышение прав, проверку email и атомарную регистрацию.
Живой перенос и проверку входа старым паролем выполняют только после создания
проекта и получения приватного экспорта; локальная проверка не заменяет этот этап.
